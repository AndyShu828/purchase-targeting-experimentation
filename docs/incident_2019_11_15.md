# 事件记录：2019-11-15 购买埋点断档

2026-09-23 发现。本文是这个数据缺陷的完整记录：**是什么、怎么发现的、为什么早没发现、
它改掉了哪些已有结论、以及为此加了什么防护**。

所有数字在全量（109,950,743 行）上实测，查询在
[`sql/analysis/`](../sql/analysis/) 下，可用 `python scripts/run_sql.py <file> --full` 复现。

---

## 1. 缺陷本身

| | |
| --- | --- |
| 现象 | 2019-11-15 一整天没有一条 `purchase` 事件 |
| 精确边界 | 最后一条购买 **2019-11-14 18:09:37 UTC**，下一条 **2019-11-16 08:32:34 UTC** |
| 持续时长 | **38.4 小时** |
| 同期其它事件 | 浏览和加购**全程正常，且处于历史最高水平**（当天 6,220,416 事件、483,305 次加购） |
| 波及范围 | 全量 61 天里，购买数低于 1 万的**只有这一天** |

**成因不能从数据里判定。** 数据集作者在
[Kaggle 讨论区](https://www.kaggle.com/datasets/mkechinov/ecommerce-behavior-data-from-multi-category-store/discussion)
被问到同一件事时回答：最可能是零售商前端的埋点故障。

所以它是**数据缺陷**，不是业务现象 —— 这一点和同期 11/15–17 的 3.5 倍流量尖峰（`data_quality.md` 检查六）
性质不同，两者恰好同时发生，这也是它被掩盖的原因之一。

## 2. 为什么早没发现

**那个 0 一直印在我们自己的输出里。** `daily_activity.sql` 有 `purchase_events` 这一列，
11-15 那行读作 0，从第 3 步跑出来的第一天起就在那里。

没有任何东西对它报警，原因是：

1. **此前所有自检都是「加总对得上」型的。** 三类事件相加 = 109,950,743、
   按会话分组与按日分组殊途同归 —— **一个 0 不破坏任何加总**。
2. **没有任何检查对「每天每类事件的最小值」有断言。** 61 天 × 8 列约 500 个数字，全靠眼睛扫。
3. **注意力被尖峰占住了。** 当时在追「尖峰是不是黑五」，看的是 `event_count` 那一列。
   11-15 在总量上是个**高峰**，所以它被读成「热闹的一天」，没被读成「坏掉的一天」。
4. **下游分析都跨整段时间聚合**，把两个月压成一张表，缺一天在结果里看不出来。

一条可迁移的教训：**总数核对守的是上游，抓不到「该有东西的格子空着」。**
（同族：`data_quality.md` 检查四的结论 58 —— `CASE` 的「漏」靠 `ELSE` 兜、「重」只有边界值测试抓得到。）

## 3. 加的防护

[`data_quality_daily_event_anomalies.sql`](../sql/analysis/data_quality_daily_event_anomalies.sql)
（`data_quality.md` 检查八）。三个设计点：

- **先造格子，再左连接。** `GROUP BY event_date, event_type` 对一个一行都没有的组合**不会产生行**，
  也就是说最值得抓的情况恰好会自己消失。先把日期与事件类型做笛卡尔积，再把计数 `LEFT JOIN` 上去，
  让「没有行」变成显式的 0。改成 `INNER JOIN` 就把这个发现删掉了。
- **每类和自己比。** purchase 比 view 少两个数量级，同一条水平线会把每个 purchase 日都判异常。
- **零行即健康。** 它回答的是一个是非问题，只返回它有意见的行。

**它的盲区**：格子是用「数据里出现过的取值」造的，所以整段窗口里都不存在的取值看不见。
`remove_from_cart` 正是这种情况 —— 数据源把它列为本数据集的事件类型之一，这两个月里一条都没有。
**这类缺失任何基于这张表的 SQL 都查不出来，只能靠源文档。**

## 4. 对已有结论的影响

### 4.1 弃购率漂移 —— 基本推翻

原结论（结论 53）：弃购率从十月的 49.6% 涨到 11/15–30 的 65.0%，是显著的行为漂移。

重算方式：剔除**与断档窗口重叠的整段会话**。查询
[`cart_abandonment_outage_sensitivity.sql`](../sql/analysis/cart_abandonment_outage_sensitivity.sql)。

| 窗口 | 加购对 | 原始 | 剔除的对 | 修正后 |
| --- | ---: | ---: | ---: | ---: |
| 10/01–07 | 112,445 | 49.0222% | 0 | 49.0222% |
| 10/08–31 | 473,733 | 49.6214% | 0 | 49.6214% |
| 11/01–14 | 470,622 | 58.8976% | 47,530 | **54.2986%** |
| 11/15–30 | 1,392,150 | 65.0009% | 385,154 | **51.7380%** |

**十一月对十月的差距从 15.4pp 缩到约 2.1pp。** 十一月仍略高（11/01–14 修正后 54.30% 是四个窗口里最高的），
所以「十一月和十月不同」成立，「差 15 个点」不成立。

**剔除单位是会话，不是事件、也不是自然日**，理由见 5.1。

一个验证点：原始那一列的四个数与 `cart_abandonment_by_category.sql` 文件头里早就记下的数字**逐位一致** ——
这说明重建的管道与原查询等价，修正后的数才可信。

### 4.2 「11-11 这批人复购最差」—— 结论不变，而且更硬

原结论（结论 64）：11-11 cohort 的 k=1 复购率 7.17%，是表里最低，推测是大促带来的低意向新客。
原证据是跨 cohort 比较，而 cohort 之间有两件事同时在变：人不同，k=1 落的日历周也不同。

重算方式：把这个 cohort 按**首购日**拆开。**同一 cohort 内部各天的 k=1 落在同一个日历周（11-18），
日历效应被固定住**，剩下的差异就只是人的差异。查询
[`weekly_cohort_first_purchase_day.sql`](../sql/analysis/weekly_cohort_first_purchase_day.sql)。

| 首购日 | 人数 | k=1 复购率 |
| --- | ---: | ---: |
| 11-11 | 9,527 | 8.1558% |
| 11-12 | 8,426 | 8.7705% |
| 11-13 | 8,269 | 9.5900% |
| 11-14 | 8,194 | 9.4093% |
| **11-15** | **无此行** | 断档，当天无人首购 |
| 11-16 | 32,399 | 7.1237% |
| 11-17 | 79,339 | 6.4256% |

大促尖峰两天占该 cohort 的 **76.5%**，复购率明显低于前四天 —— cohort 级的 7.17 主要是这两天的权重。

**断档对它的影响方向是分母**：首购落在断档里的人没有首购记录，除非当周又买过一次，
否则整个人不在这个 cohort 里。**分母偏小会把复购率抬高，所以真实值 ≤ 7.17，修正只会让结论更强。**

规模估计约 3 万人（对 146,154 的 cohort）：断档期 226,123 人加过购，其中 15.72% 到窗口结束仍无购买记录；
紧随其后、同样长度、同样繁忙的大促窗口（11-16 08:32 → 11-17 22:56，埋点正常，231,507 人加购）
这个数字是 2.29%，差 13.4pp。**这只是数量级** —— 控制窗口紧挨断档，吸收了被推迟的需求，所以估计偏保守。

**反向影响在 11-18 那个 cohort**：断档期购买没被记录、之后又买的人，会以「新客」身份进入后面的 cohort。
所以 11-11（7.17）与 11-18（11.36）之间的反差被夸大了，夸大多少查不出来。

### 4.4 复购间隔（结论 ⑯）—— 原数字变成上界

原结论：八成复购在**事件级 6 天 / occasion 级 12 天**内完成，两个口径差一倍。

重算方式：剔除**跨度与断档窗口重叠的整条间隔** —— 本该把它切成两段的那次购买可能没被记录。查询
[`repurchase_interval_outage_sensitivity.sql`](../sql/analysis/repurchase_interval_outage_sensitivity.sql)。

| 口径 | 间隔数 | 剔除 | 6 天内（原始） | 6 天内（修正） | 80% 分位（原始） | 80% 分位（修正） |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 事件级 | 962,318 | 81,419 | 80.15% | 86.38% | **5.96 天** | **3.63 天** |
| occasion 级 | 607,754 | 81,419 | 68.56% | 77.21% | **10.88 天** | **6.95 天** |

**两个口径剔除数相同不是抄错**：跨过这个洞的间隔，每个「洞两侧都有购买」的用户各有一条，
而且跨越 38.4 小时的间隔必然超过 1,800 秒的 occasion 阈值，所以两边是同一批用户。

🔴 **修正是过度修正，所以要读区间而不是读点。** 剔除跨洞间隔时，
也剔掉了那些「本来就长、只是恰好跨过 11-15」的真实间隔，而它们按定义就是长的。
所以**原始值偏低、修正值偏高，真值在两者之间**：事件级 3.63–5.96 天，occasion 级 6.95–10.88 天。

**活下来的是比值**：10.88 / 5.96 = 1.83，6.95 / 3.63 = 1.91。
**「两个口径差一倍」在区间两端都成立**，而「6 天 / 12 天」这组绝对数字是**上界**，不是估计值。

### 4.5 会话漏斗（结论 ⑰ 所在的表）—— 总购买率几乎不动，加购→购买一步动了 8pp

重算方式：与 4.1 相同，剔除**与断档窗口重叠的整段会话**。查询
[`session_funnel_outage_sensitivity.sql`](../sql/analysis/session_funnel_outage_sensitivity.sql)。
原始列与 `session_funnel.sql` 文件头的六个数逐位一致。

| 步骤 | 松口径（原始 → 修正） | 严口径逐步转化（原始 → 修正） |
| --- | ---: | ---: |
| 会话 | 23,517,313 → 22,258,942 | — |
| view | 99.93% → 99.94% | 99.93% → 99.94% |
| cart | 9.91% → 8.73% | 9.87% → 8.69% |
| purchase | **5.98% → 6.31%** | **40.45% → 48.50%** |

剔除 1,258,371 个会话（5.35%）。**会话购买率只动了 0.33pp，严口径的加购→购买一步动了 8.06pp。**
原因是被剔的会话**加购率 30.93%、转化率 0.31%**（387,890 次严口径加购，只有 1,215 次购买）——
它们往分母里塞了一大块「加购了但不可能被记录为购买」的会话。

**这不是过度修正**（和 4.4 不同）：会话是按「什么时候发生」被剔的，不是按「结果如何」，
所以修正列对剩下的人群是无偏的。变的是**人群**：剔掉的正好是 11/15–17 尖峰的开头。
view 和 cart 两行没有被断档直接影响，它们的变化量就是这次构成变化的大小。

**没解释的**：被剔会话的加购率为什么是其余的 3.5 倍。尖峰能解释一部分（11-15 当天加购占事件 7.8%，
全窗口 3.6%），但「结不了账的人反复加购」也会产生同样的数字，数据分不开。

**结论 ⑰（三成购买会话没加购过所买商品）几乎不受影响**：被剔的购买会话只有 1,321 个（0.094%），
四行分解里任一比例的移动不超过这个量级。断档期根本没被记录的购买，任何过滤都找不回来。

### 4.3 P3 测试集与 P4 实验设计 —— 窗口改了

> **截止日语义（2026-09-24 统一）**：截止日 = 标签窗口 / 观察期的**第一天**，沿用计划原文。
> 特征取 `event_time < cutoff`，标签取 `>= cutoff`。P2 特征函数的 `cutoff` 参数只有这一种含义 ——
> 差一天就是泄漏或丢一天数据，而且不报错。

计划原文：打分截止 11/15，观察期 11/15–11/28。**不能用**，三个理由：

| 受影响的部分 | 保留原窗口会怎样 |
| --- | --- |
| 主指标（观察期转化率） | 第一天恒为 0、第二天只剩 15.5 小时有效 —— 两臂同时被拉低，检验功效白白损失 |
| 特征 / 打分 | 「最近 N 天购买次数」对断档期活跃的用户系统性偏低。**这是协变量污染**，影响分层和平衡性检查 |
| 外部效度 | 11/16–17 是大促尖峰，新客构成与平时不同（见 4.2），观察期骑在尖峰上 |

**新设计（2026-09-23 定，2026-09-24 按上面的语义改写）**：截止日 **11-18**，观察期 **11/18–11/30**（13 天）。
同时避开断档和尖峰，数据到 11-30 正好用满。补满 14 天只能下载 12 月数据（2.74 GB 压缩包），
会推翻沙盒 10 GB 额度和已定的导入方案，不做。

**P3 测试集跟着移（2026-09-24 定）**：计划原文的测试截止日 11-15（标签 11/15–11/28）会让标签缺 32.54 小时（9.7%）——
只在断档期买过的人被标成 0。改为和 P4 同一个截止日：

| 用途 | 截止日 | 特征窗口 | 标签窗口 | 与断档重叠 |
| --- | --- | --- | --- | --- |
| 训练 | 10-15 | 10/01–10/14 | 10/15–10/28 | 0 |
| 验证 | 11-01 | 10/18–10/31 | 11/01–11/14 | 标签缺 5.84 小时（1.7%），接受，报告注明 |
| 测试 | **11-18** | 11/04–11/17 | 11/18–11/30（13 天） | 特征含整段 38.38 小时（11.4%），标签 0 |

测试集 = P4 打分人群，一套特征两处用。代价：任何 14 天特征窗口只要跨过 11-14 → 11-16，就整段覆盖断档，
所以只能在「特征干净、标签脏」和「标签干净、特征脏」之间选 —— 选了后者，特征侧的修正见下面第 1 条。
13 天标签的正例率天然偏低；标签含黑五（11-29 购买约 +30%）—— 跨集合比较时在 `model_report.md` 说明。

**换了窗口也躲不掉的两条**：

1. 特征窗口 10/01–11/17 仍然覆盖断档。比率型特征要把那 38.4 小时从分母里扣掉；
   短窗口特征（「最近 3 天购买」）结束点落在断档附近的一律不能用 —— **决定不用**，趋势组只用「近 7 天 / 前 7 天」。
   「加购未购比例」会被断档虚高（加了购、购买记不到）：会话层加 `is_outage_session` 标记列
   （沿用 `session_funnel_outage_sensitivity.sql` 的重叠判断），计算时排除，标记列留给 P4 复用。
2. 按「首购是否在大促周」分层或查平衡 —— 大促新客行为不同（4.2 已证），
   两臂这个比例失衡会偏出一个效应。

**敏感性分析**：用原来的 11/15 起点再跑一遍做对比，把「忽略这个缺陷会得到什么」量化出来。

## 5. 两条方法论

### 5.1 过滤的位置由「被过滤对象的粒度」决定

要剔的单位是会话，`WHERE` 就必须写在**会话粒度存在之后**（30 分钟切分之后，
用 `session_start` / `session_end` 判重叠），不能写在事件层。写在最内层有两个错，都不报错：

1. **它会改变会话切分本身。** 会话是靠「相邻事件间隔 > 30 分钟」切出来的。
   在切分**之前**删掉一批事件，剩下事件之间的间隔就变了，切出来的边界跟着变。
   **你过滤的是事件，被改掉的是会话的定义。**
2. **它只删窗口内的那一段，跨边界的会话还留着半截。** 那半截依然是坏的 ——
   它后半段本该记录的购买没了。

按自然日剔同样不对：断档从 11-14 18:09 开始，11-14 傍晚的会话也是坏的。

**重叠不是包含**：`session_start < 窗口结束 AND session_end > 窗口开始`。只沾上一点的会话也算脏。

### 5.2 先判偏差方向，常常不必精确修正就能定结论

4.2 里断档让 cohort 少了人，**分母偏小 ⇒ 复购率被抬高 ⇒ 真实值只会更低**。
「这批人复购最差」这个结论因此不需要精确修正就能确认 —— 修正只会让它更强。

反过来 4.1 里断档制造的是假弃购，**方向是抬高弃购率**，所以必须精确剔除才能知道还剩多少。
**方向和结论同向时可以只报方向，反向时必须算。**

## 6. 边界与未决

- **窗口边界是观测值，不是真值。** 18:09:37 是最后一条购买、08:32:34 是第一条恢复后的购买，
  真实故障区间应在两点之间稍窄。用观测边界会**略微多剔**，方向上偏保守。
- **11 月其余日子未逐一体检。** 检查八现在只对「为 0」和「偏离自身日均 4 倍 / 四分之一」报警，
  更温和的埋点退化（比如某天只丢三成购买）它抓不到。
- **⑤ 会话漏斗已重算（见 4.5）。** 此前这里写的「影响约 3%」是没跑之前的估计，
  对会话购买率只是量级接近（实测 +0.33pp、相对 +5.6%，剔除的会话占 5.35%），
  而且**漏掉了加购→购买那一步的 8.06pp**。
- **P2 特征、P3 模型尚未开始**，但 4.3 的两条约束在动工时必须带上。
