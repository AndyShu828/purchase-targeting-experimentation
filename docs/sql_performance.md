# BigQuery 裁剪实测：分区、相关列、聚簇

表：`pte.events`，2019-10 全月，42,448,764 行，5.58 GB 逻辑字节，
`PARTITION BY RANGE_BUCKET(day_index, …)` + `CLUSTER BY event_type, user_id`（见
[`sql/ddl/create_events.sql`](../sql/ddl/create_events.sql)）。
脚本：[`scripts/bench_bigquery.sh`](../scripts/bench_bigquery.sh)，2026-09-23 实测。

五个变体问的是同一类问题（某个范围内的事件数与金额和），只有 `WHERE` 不同。
**每次都带 `--nouse_cache`** —— 命中缓存的查询计费 0 字节，会让所有变体看起来都免费。

| 变体 | dry run 字节 | 实际计费字节 | 耗时 | 扫到的行 |
| --- | ---: | ---: | ---: | ---: |
| 1. 无过滤 | 679,180,224 | 679,477,248 | 109 ms | 42,448,764 |
| 2. `event_date` 过滤（普通列） | 247,634,928 | 248,512,512 | 57 ms | 10,318,122 |
| 3. `day_index` 过滤（分区键） | 247,634,928 | 248,512,512 | 79 ms | 10,318,122 |
| 4. `day_index` + `event_type`（再加聚簇首列） | 82,174,774 | 82,837,504 | 18 ms | 186,856 |
| 5. `brand` 过滤（既非分区也非聚簇） | 967,293,638 | 967,835,648 | 61 ms | 5,282,775 |

变体 2 和 3 的**返回行完全相同**（脚本里用 `diff` 核过）—— 这是字节差可归因于「过滤怎么写」而不是「问的问题不同」的前提。

---

## 结论一：`event_date` 和分区键 `day_index` 裁剪效果完全一样 —— 这推翻了一个预判

改用整数分区时我写过：「裁剪要靠 `day_index` 过滤，按 `event_date` 过滤会全表扫」。**实测不成立**，两者字节数一字不差。

算一下就知道它确实裁了：变体 2 扫 10,318,122 行，每行读 `price`（NUMERIC，16 B）和 `event_date`（8 B）：

```
10,318,122 × 24 = 247,634,928   ← 与 dry run 报的数字完全相等
```

如果没裁剪，`price` 要读满 42,448,764 行（679 MB）再加上 `event_date` 一整列，超过 1 GB。

**机制**：BigQuery 对每个存储块记录各列的最小值/最大值，查询时跳过不可能命中的块。
而我们**每个分区正好由一天的文件导入**，所以 `event_date` 与 `day_index` 完全相关 —— 按日期过滤时，
块统计足以判断哪些块可跳过。

⚠️ **这是导入方式带来的巧合，不是保证。** 哪天有一次导入把多天混进一个分区，
或者数据以别的顺序写入，这种相关性就没了，而**分区键的裁剪仍然成立**。
所以结论是：`day_index` 是**有保证的**机制，`event_date` 是**当前物理布局下碰巧有效**的。
要写进生产管道的过滤条件，用前者。

## 结论二：聚簇在分区之上再省 3 倍

变体 3 → 4，多加一个 `event_type = 'purchase'`：字节从 247.6 MB 降到 82.2 MB，**再省 3.0 倍**，耗时 79 ms → 18 ms。

但注意它**没有降到理论下限**。目标行只有 186,856 行，而扫描量对应约 265 万行 ——
聚簇是**按块**跳过的，一个块里只要有一行 purchase，整块都得读。
**分区是文件级的隔离，聚簇是块级的排序**：后者更细但不精确，别把它当索引用。

## 结论三：对没有任何索引的列过滤，比不过滤还贵

变体 5 按 `brand` 过滤，**967 MB，比全表无过滤的 679 MB 还多 42%**。

原因是列存：`WHERE` 里出现的列**必须被读出来**才能比较。`brand` 不是分区键也不是聚簇列，
一行都跳不过，于是在原本要读的 `price` 之外，又整列读了一遍 `brand`（变长字符串，比 `price` 还宽）。

**「加过滤条件 = 更快更便宜」在列存数据库里不成立。** 只有当过滤能让引擎**跳过数据**时才成立；
否则它只是多读一列。

## 结论四：dry run 不是账单

| 变体 | dry run | 计费 | 差额 |
| --- | ---: | ---: | ---: |
| 1 | 679,180,224 | 679,477,248 | +297,024 |
| 4 | 82,174,774 | 82,837,504 | +662,730 |

计费**向上取整到 MiB**（82,837,504 = 79 MiB 整），另外还有**每次查询 10 MB 的最低计费**
（P0 已实测过：dry run 说 2,747,362 字节，账单是 10,485,760）。
所以 dry run 用来判断「这条查询会不会扫爆」是准的，用来估算账单则**总是偏低**。

## 「排序宽度」复测：结论 ⑫ 成立，而且这次换了高基数列

结论 ⑫ 曾用 `category_code`（129 个不同值）测「把标签一路带下来会不会变慢」，**没测出差别**。
当时的解释是 129 个值字典编码后几乎不占宽度，所以「宽度」这个说法根本没被检验到。
这次换成真正带不动的列重测，脚本 [`scripts/bench_sort_width.py`](../scripts/bench_sort_width.py)：

| 变体 | run1 | run2 | run3 | run4 | run5 | run6 | min | 均值 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 不带额外列 | 12.7 | 11.1 | 12.0 | 12.0 | 11.6 | 13.9 | 11.1 | **12.2** |
| 带 `category_code`（129 值） | 11.4 | 11.1 | 12.9 | 12.7 | 10.6 | 12.9 | 10.6 | **11.9** |
| 带 `product_id`（16.6 万值） | 11.4 | 11.2 | 11.7 | 13.4 | 12.6 | 12.9 | 11.2 | **12.2** |
| 带 `user_session`（2300 万值） | 12.1 | 11.4 | 12.9 | 12.7 | 12.2 | 12.3 | 11.4 | **12.3** |

**基数跨越五个数量级，均值差 0.4 秒，落在每个变体自身的波动里（10.6–13.9）。**
⇒ 结论 ⑫ 维持：在这条管道、这份数据上，「带一列下来」的代价测不出来。

### 这个数字是第四版设计才得到的，前三版都给出了「漂亮但错」的结果

| 版本 | 设计 | 看到的结果 | 问题 |
| --- | --- | --- | --- |
| 1 | 一个变体连跑四轮，再换下一个 | 完美单调：32.8 / 40.2 / 59.1 / 68.6 秒 | **变体顺序 = 时间顺序**，而 narrow 自己四轮从 18.3 漂到 41.4 |
| 2 | 轮转（每轮四个变体各一次） | 仍单调 | 轮内顺序固定，每个位置约 +4 秒，**和要测的效应同量级** |
| 3 | 轮转 + 逐轮反向 | 趋势消失（均值差 1.5 秒），但每个变体自己 12 → 66 秒 | 漂移仍在，只是被抵消了 |
| 4 | **每次测量一个全新进程** + 逐轮反向 | 均值差 0.4 秒，**每次都是 12 秒左右** | —— |

**漂移的来源查清了，是三个假设之外的第四个。** 依次排除：

- **不是温度降频**：运行中采样 `% Processor Performance` 一直是 **100–109%**（标称频率以上）
- **不是溢写**：运行中 `data/tmp` 始终 0 字节（此前「跑完再看是空的」是个无效检查 —— 溢写文件跑完就删）
- **不是内存不足**：空闲内存 19 GB，而且 **CPU 占用只有 20–29%**，16 线程里大约只有 4 个在忙
- ✅ **是进程内累积的状态**：同一进程连跑同一条查询六次，**11.9 → 33.5 秒**；
  换成三个独立进程各跑一次，**11.5 / 11.2 / 11.8 秒**

所以脚本最终的形状是：**父进程按反向轮转的顺序，为每一次测量拉起一个子进程**。

### 可迁移的三条

1. **一条「干净的单调趋势」最可能的解释是测量设计，不是被测对象。** 前三版都给出了这种趋势。
2. **控制实验是最便宜的诊断**：同一个变体连跑六轮，一次就把「变体差异」和「会话漂移」分开了。
3. **排除假设要在运行中测，不是跑完测。** 「跑完 temp 目录是空的」证明不了没溢写。

## 分区红利的边界（DuckDB 全量，2026-09-20 实测）

分区省掉的是**分组**，不是**聚合**：

| 查询（全量 1.1 亿行） | 耗时 |
| --- | ---: |
| 按分区键 `GROUP BY` + 三个条件计数 | **0.277 s** |
| 同上 + 两个 `COUNT(DISTINCT)`（`user_id` / `user_session`） | **5.462 s** |

**19.7 倍的差全在高基数去重上。** 分区键做 `GROUP BY` 时每个分区就是一个组，不需要哈希也不需要跨分区重排 ——
这部分开销被消掉了；但去重本身该做多少还是多少。

⇒ 面试里讲「分区让查询快 N 倍」不如讲「**我量了分区消除了哪一部分、没消除哪一部分**」。

## `SAFE_DIVIDE` 与 `APPROX_COUNT_DISTINCT`（2026-09-23 两边实测）

计划点名要熟悉的四个 BigQuery 差异，这是最后两个（`QUALIFY`、时间差参数顺序见
[`sql_dialects.md`](sql_dialects.md)）。

### 零分母：三种写法都给 NULL，但只有一种两边通用

| 写法 | BigQuery | DuckDB |
| --- | --- | --- |
| `1 / 0` | **运行期报错** `division by zero` | `inf`（默认开 `ieee_floating_point_ops`） |
| `SAFE_DIVIDE(1, 0)` / `SAFE_DIVIDE(0, 0)` | `NULL` / `NULL` | **函数不存在** |
| `1 / NULLIF(0, 0)` | `NULL` | `NULL` ✅ |

所以 `sql/analysis/` 里统一用 `NULLIF`。`SAFE_DIVIDE` 更短，但它是单边方言，本地跑不了。

⚠️ 裸除零是**运行期**错误，`--dry_run` 显示「successfully validated」，
所以它只能靠读代码或者真跑发现 —— 这是结论 52 的完整形态。

### 近似去重：省的是时间，不是字节；而且两边精度差一个量级

BigQuery，同一张表的 `user_session`（923 万个不同值，10 月）：

| | 结果 | 计费字节 | 墙上时间 | slot 时间 |
| --- | ---: | ---: | ---: | ---: |
| `COUNT(DISTINCT user_session)` | 9,244,421 | 1,613,758,464 | 935 ms | 36,714 ms |
| `APPROX_COUNT_DISTINCT(user_session)` | 9,210,802（**−0.36%**） | **1,613,758,464（一样）** | **150 ms** | **11,158 ms** |

**计费字节完全相同** —— 近似算法省的是算，不是读。按扫描字节计费的按量模式下，
它**不省钱、只省时间**（墙上 6.2 倍、slot 3.3 倍）；按容量（slot）计费才省钱。

同一组数据在 DuckDB 上：

| 列 | 精确 | DuckDB 近似 | 误差 | BigQuery 近似 | 误差 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `user_session` | 9,244,421 | 11,390,309 | **+23.2%** | 9,210,802 | −0.36% |
| `user_id` | 3,022,290 | 3,455,844 | **+14.3%** | 3,023,684 | +0.05% |

🔴 **「近似」在两个引擎上不是同一个精度档位。** BigQuery 的误差在千分之几，
DuckDB 1.5.5 的误差是百分之十几 —— 拿本地的近似值对账会被误导。
**本地一律用精确去重，近似只在 BigQuery 上、且只在能接受千分之几误差时用。**

## 复现

```bash
scripts/bench_bigquery.sh
```

在 WSL 里跑（`bq` 装在那边）。五个变体各跑一次 dry run 和一次真查询，合计约 2.7 GB 计费字节，
沙盒每月 1 TB 额度下可以忽略。

**脚本自身的两个坑**（都撞过）：

- `bq show -j <job>` **必须带 `--location`**，否则查不到作业、**不报错**、返回空 —— 第一版脚本因此输出了一张空表，而退出码是 0。
- 真查询必须带 `--nouse_cache`。第二次跑同样的查询会命中缓存，计费 0 字节。
