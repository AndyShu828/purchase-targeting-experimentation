DuckDB 和 Spark 依次跑，不同时占 CPU；计时期间机器上没有别的负载（这一点要刻意保证，见第 5 节）。

**正确性**：每个截止日、每个组，两边的输出按 `user_id` 逐列比对（浮点允许 1e-9）——**18 组全部 0 行差异**。

## 1. 结果：DuckDB 快 1.4–5 倍

中位秒数，DuckDB / Spark（倍数 = Spark ÷ DuckDB），2026-09-26 实测：

| 组 | 测试 11-18 | 训练 10-15 | 验证 11-01 | 这组在做什么 |
| --- | --: | --: | --: | --- |
| 活跃度 | 1.1 / 4.2（3.8×） | 0.6 / 2.5（4.2×） | 0.5 / 2.5（4.6×） | 按用户计数 |
| 购买 | 1.1 / 4.1（3.7×） | 0.5 / 2.2（4.1×） | 0.6 / 2.1（3.7×） | 按用户计数、求和 |
| 趋势 | 0.5 / 2.6（5.0×） | 0.3 / 1.3（5.0×） | 0.3 / 1.2（4.5×） | 两段计数相除 |
| 会话 | 10.8 / 15.6（1.4×） | 4.9 / 6.9（1.4×） | 5.1 / 7.2（1.4×） | 切会话（窗口函数） |
| 意向 | 11.8 / 25.3（2.1×） | 4.9 / 8.2（1.7×） | 4.6 / 8.5（1.9×） | 切会话 + (会话, 类目) 对 |
| 偏好 | 19.1 / 34.6（1.8×） | 7.4 / 17.5（2.4×） | 7.5 / 18.9（2.5×） | 类目内排名、主类目、切会话 + 转化率 |

测试截止日的特征窗口含 11/15–17 的大促尖峰，事件最多，所以三列里它最慢。

## 2. 读法

**结论一：任务越重，差距越小。** 按用户计数的轻任务 Spark 慢 4–5 倍，要切会话的重任务只慢 1.4–2.5 倍。
Spark 每个任务都有一笔和数据量无关的固定开销（生成计划、调度 stage、启动 task），任务越轻，这笔开销占比越大。

**结论二：Spark 的第一次明显慢，中位数把它挡掉了。** DuckDB 三次几乎一样；Spark 第一次常慢一截
（测试截止日活跃度 8.7 → 4.2 / 4.1 秒），这是 JVM 即时编译和首次读取的预热。只跑一次就下结论，会把 Spark 算得更慢。
第 2、3 次之间相差 ≤ 10%。

**结论三：Spark 大量写盘，DuckDB 几乎不写。** 整次计时（三个截止日 × 六组 × 两个引擎 × 3 次）约 **37 GB** 写进 WSL 虚拟盘，
几乎全是 Spark 的 shuffle 文件；同期 DuckDB 进程只写了 0.2 GB。切会话要按用户重新分区，Spark 把几千万行中间结果写到本地临时文件再读回来，
DuckDB 在内存里做完。（02:01 之后是磁盘计数器实测的 29.7 GB，之前 3.5 分钟按进程计数估约 7.6 GB。）

**结论四：Spark 的内存要手动给。** 本地模式下所有 task 跑在 driver 的 JVM 里，默认堆 1 GB；
14 天窗口上切会话时 `OutOfMemoryError`，设成 8 GB 后正常（2026-09-25）。DuckDB 不需要调任何参数。

## 3. 一次 Spark 优化：shuffle 分区数与 broadcast join

计划 v2 要求「记录一次 Spark 优化（shuffle 分区数或 broadcast join），记前后耗时」。做了两个
（[`scripts/bench_spark_tuning.py`](../scripts/bench_spark_tuning.py)）：

- **A. shuffle 分区数，2×2**：AQE 开 / 关 × `spark.sql.shuffle.partitions` 200 / 16（16 = 这台机器的核数）。只测偏好组和会话组
- **B. broadcast join**：人群 `LEFT JOIN` 特征聚合表。**左连接只能广播右边**，也就是每个用户一行的聚合表（230 万行），
  它远超 10 MB 的默认阈值，所以默认走 SortMergeJoin。把阈值调到 512 MB 强制广播。只测活跃度组（结构最简单）

设计：所有配置在同一个 Spark 会话里切换运行时参数；先跑一轮预热丢弃，之后每轮把所有配置轮流跑一遍（让漂移平均落到每个配置上）；
每次记录耗时、shuffle 写入量、读 shuffle 的任务数、最终计划里实际用的 join。每个配置的输出都和基线逐用户比对，**全部 0 行差异**。

**开跑前的事实**：默认就是 200 分区 + AQE 开（Spark 4 默认）；实际读 shuffle 的任务只有 15–17 个 —— **AQE 已经在运行时把 200 个分区合并成约 16 个**。
偏好组的最终计划里，AQE 还把一张 652 行的小表（类目转化率）的 join 自动改成了 broadcast。

**Andy 的预测（开跑前写下）**：AQE 开 + 16「几乎没变化」；AQE 关 + 200「显著变慢」；AQE 关 + 16「几乎没变化」；broadcast「快 40% 左右」。

**结果**（测试截止日，中位秒数；会话组因为第一次跑基线离散偏大，倒过顺序重跑了一次）：

| 配置 | 预测 | 偏好组 | 会话组（第一次 / 倒序） | shuffle 写入 偏好 / 会话（GB） | 对上了吗 |
| --- | --- | --: | --: | --: | --- |
| 基线：AQE 开 + 200 | — | 38.5 | 17.0 / 15.3 | 2.35 / 1.05 | |
| AQE 开 + 16 | 几乎不变 | 41.3 | 13.3 / 14.1 | 2.79 / 1.31 | ✅ |
| AQE 关 + 200 | 显著变慢 | 40.7 | 12.5 / 14.0 | 2.50 / 1.07 | ❌ 没变慢 |
| AQE 关 + 16 | 几乎不变 | 36.5 | 13.2 / 14.4 | 2.84 / 1.31 | ✅ |

| 配置 | 预测 | 活跃度组 | shuffle 写入（GB） | 对上了吗 |
| --- | --- | --: | --: | --- |
| 基线（SortMergeJoin） | — | 4.2 | 0.19 | |
| broadcast（BroadcastHashJoin） | 快 40% | **4.9（慢 17%）** | 0.19 | ❌ 方向反了 |

同一配置 3 次之间相差 5–10%，所以 **10% 以内的差别不作结论**：四种分区配置之间没有可靠的差别。
会话组的基线两种顺序下都最慢（+28%、+9%），但幅度不稳，3 次运行分不清是效应还是噪声。

**为什么关掉 AQE、用 200 个分区也没变慢。** 偏好组约 2.4 GB 的 shuffle 分成 200 份，每份约 12 MB；这样的任务调度开销是毫秒级，
200 个任务在 16 核上跑约 13 轮，总共多出不到一秒，相对 30–40 秒可以忽略。「200 太多要调小」适用于数据很小、
每个分区只有几 KB 到几 MB、任务开销占主导的时候；「分区太少会溢写」适用于数据很大的时候。这里在两者之间，默认值已经合适。

**为什么 broadcast 反而慢了：它一次 shuffle 都没省掉。** 两个最终计划里 shuffle（`Exchange hashpartitioning`）都是 3 次：
人群的 `DISTINCT user_id` 1 次，特征聚合 2 次（`COUNT(DISTINCT event_date)` 要两步聚合）。SortMergeJoin 要求两边按 `user_id` 分区，
而两边**在 join 之前已经为了各自的聚合按 `user_id` shuffle 过**，Spark 直接复用这个分区，join 本身只加了两次排序。
强制 broadcast 省掉的就是这两次排序，却要把 230 万行的右表收集到 driver、建哈希表、再发给每个 task —— 得不偿失。
shuffle 写入量 0.19 → 0.19 GB 一点没变，就是这个原因。

一般来说，一次 broadcast join 最多省掉两次 shuffle（左右两边为对齐分区各做的一次），**前提是这些 shuffle 只为这次 join 而做**；
上游已经按 join 键分好区时，一次也省不掉。它最划算的场景是大表和一张很小的表 join、而大表还没按 join 键分过区。
「快 40%」隐含了「join 占这组耗时的四成」，实际上 join 几乎没有自己的开销。**先看时间花在哪一步，再决定优化哪一步。**

**顺带观察到、没有解释的**：分区数设成 16 时 shuffle 写入量反而更多（偏好组 2.79–2.84 对 2.35–2.50 GB，会话组 1.31 对 1.05–1.07 GB），
两次运行都一样。原因没有查。AQE 关掉后，偏好组那个 652 行的自动 broadcast 也没了（1 个 BroadcastHashJoin + 3 个 SortMergeJoin → 4 个 SortMergeJoin），
耗时不受影响，因为那张表太小。

**一句话**：在这个数据量下 Spark 的默认配置已经够好；手动调分区、强制 broadcast 都没有带来可靠的收益，其中 broadcast 还变慢了。
这次的价值在于知道**为什么**没有收益，以及在什么条件下它们才会有收益。

## 4. 单机上为什么还用 Spark（待 Andy 审）

实测说得很清楚：**在 1.1 亿行、一台 32 GB 的机器上，DuckDB 更快、更省事、不写盘。** 如果只为这一份数据，用 DuckDB 就够了。
项目里仍然用 PySpark 写特征管道，理由是：

1. **代码能原样扩到集群。** 同一组特征函数换一个 `SparkSession` 就能跑在多机集群上；DuckDB 受单机内存和磁盘限制。
   这里的 1.4–5 倍差距是固定开销造成的，数据量上去之后，这笔开销的占比会下降（结论一已经显示出这个趋势）
2. **两份独立实现互为对账。** SQL 版和 Spark 版由不同的人、用不同的引擎写，18 组逐用户 0 差异；
   翻译过程中抓到的分歧（NULL 会话被 JOIN 丢掉、`0.0 / 0` 在 DuckDB 得 NaN 而 Spark 报错等）都是单一实现发现不了的
3. **计划要求。** 这是练 PySpark 的项目；工程类在面试里的比重不高，能讲清上面两条和第 3 节就够了

没做的：在内存更小的机器（比如 8 GB 的笔记本）上重跑。那种环境下 DuckDB 也要溢写，差距可能缩小甚至反转，更能说明 Spark 的价值；
HANDOFF 第 4 节记过这个备选，这次没做。

## 5. 局限与教训

- 只有一台机器、每个配置 3 次运行；10% 以内的差别不作结论
- **计时期间不能有别的重负载。** 这一点是踩出来的：此前几次单次计时和全量查询、全套测试并行，耗时全部作废（对账结论不受影响：并行只改变快慢，不改变结果）
- 会话组第一次的基线离散偏大，所以倒序重跑确认；以后这类实验一开始就应该跑两种顺序
